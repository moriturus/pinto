Summary

Allow action items recorded in a Retro or Review to become ordinary PBIs linked to their source child record, so follow-up work uses the existing backlog workflow instead of a second task system.

# Implementation Plan

- Add a typed optional PBI source link with `kind` (`retro` or `review`) and the matching Sprint ID; persist it in file/Git Markdown, SQLite, and board export JSON.
- Reuse the existing PBI creation options for `sprint retro action` and `sprint review action`: title, body/template/editor, points, labels, assignee, Sprint assignment, parent, and dependencies.
- Keep the source record as a Markdown record without a state of its own; show linked action PBI IDs, titles, and current normal PBI statuses from Retro/Review detail views in human and JSON output.
- Keep action progress entirely in the existing PBI workflow so normal `list`, `show`, `edit`, `move`, and `remove` commands remain authoritative.
- Follow Red -> Green -> Refactor with domain, persistence backend, CLI, localization, export/import, demo, and documentation coverage; verify through `cargo run` dogfooding and iterative review.

# Scope

- Support action-item promotion from either a Retro or a Review into a normal PBI.
- Preserve established PBI creation options, including title, body/template, assignee, Sprint assignment, and dependencies where supplied.
- Store a source link containing child record kind and Sprint-matching ID.
- Display linked action PBIs from the child record while their status remains managed by normal PBI commands.

# Acceptance Criteria

- [x] A Retro or Review action can create a normal PBI with existing PBI creation semantics.
- [x] Created PBI retains machine-readable link to source Retro or Review.
- [x] Retro and Review views can show linked action PBI IDs and current statuses.
- [x] Action progress controlled by existing PBI list/show/edit/move/remove, no parallel action-item state machine.
- [x] Existing PBI workflows remain usable for action PBIs without requiring Retro/Review-specific status.
