Add one first-class Retro record beneath each existing Sprint. A Retro uses the Sprint ID as its own ID, is stored in the dedicated .pinto/retro/ directory, and follows the established PBI and Sprint CLI conventions for creation, templates, editing, display, listing, and machine-readable output.

# **Implementation Plan**
- Define a Sprint Retro domain record with the Sprint ID as its stable ID, body text, and created/updated timestamps.
- Add `.pinto/retro/<SPRINT-ID>.md` Markdown/TOML persistence and a repository trait dispatched consistently by file, Git, and optional SQLite backends; keep the Retro directory separate from Sprint files.
- Add `pinto sprint retro` creation, edit, show, list, `--template`, `--edit`, and `--json` flows with localized messages, actionable errors, and Git operation-level commits.
- Add Red -> Green -> Refactor coverage for planned, active, and closed parent Sprints, missing/duplicate records, templates/editor behavior, malformed filenames, JSON output, and Git boundaries.
- Add a focused demo and update the CLI/data-format documentation without changing top-level `pinto retro` or board interchange behavior.

# Acceptance Criteria
- [x] `pinto sprint retro` is supported; no top-level `pinto retro` is required.
- [x] Each Sprint has zero or one Retro, and the Retro ID and filename match the Sprint ID.
- [x] A Retro can be created for planned, active, or closed Sprints; a missing Sprint fails clearly.
- [x] Creation accepts `--template <name>` under `.pinto/templates/retro`, and `--edit` opens the standard editor with template content as the initial body.
- [x] Retro edit, show, list, JSON output, localization, actionable errors, and Git commit behavior follow the established PBI or Sprint conventions.
