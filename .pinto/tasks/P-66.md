# **Summary**

Add one first-class Retro record beneath each existing Sprint. A Retro uses the Sprint ID as its own ID, is stored in the dedicated `.pinto/retro/` directory, and follows the established PBI and Sprint CLI conventions for creation, templates, editing, display, listing, and machine-readable output.

# **Scope**

- Expose the feature under `pinto sprint retro`; do not add a top-level `pinto retro` command.
- Allow at most one Retro for each Sprint, with the Retro ID and filename equal to the Sprint ID.
- Require the referenced Sprint to exist, but allow creation when that Sprint is planned, active, or closed.
- Support `.pinto/templates/retro/<name>.md`, `--template`, and standard-editor editing with the same creation and edit semantics as PBIs.
- Follow existing output, localization, error, Git-boundary, and JSON conventions for the child record.

# **Acceptance Criteria**

- [ ] `pinto sprint retro` is the supported command path and no top-level `pinto retro` command is required.
- [ ] A Sprint can have zero or one Retro, and the stored Retro ID and filename match the Sprint ID.
- [ ] Retro creation succeeds for an existing Sprint in planned, active, and closed states and fails clearly when the Sprint does not exist.
- [ ] Retro creation accepts `--template <name>` from `.pinto/templates/retro/<name>.md`, and `--edit` opens the configured standard editor with the template as initial content when supplied.
- [ ] Retro edit, show, list, and JSON behavior follows the established PBI or Sprint conventions, including actionable errors and localized output.
