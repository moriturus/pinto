Summary

Document predictable failure behavior for the public Rust API so library users can understand validation, persistence, and retry contracts from Rustdoc.

Implementation Plan

### Selected public API scope

- Treat public `Result`-returning operations re-exported from `pinto::service` and the public persistence facade in `pinto::storage` as the selected contract surface.
- Keep pure domain constructors and parsers outside this staged guard unless they are part of the selected persistence/service surface; avoid expanding the change into unrelated public APIs.

### Error and persistence contracts

- Add `# Errors` sections to every selected public `Result` API, naming relevant validation, missing-record, parsing, I/O, backend, and commit failures.
- State durable partial-change behavior and retry safety for destructive, multi-record, and persistence operations using the existing lock, rollback, atomic-write, and Git commit guarantees.
- Preserve the exposed `crate::error::Result<T>` contracts and document behavior without changing runtime semantics.

### Guard and verification

- Enable `clippy::missing_errors_doc` at the selected `service` and `storage` module boundaries so new omissions fail the repository warning-denied lint.
- Because RPITIT repository trait methods return `impl Future<Output = Result<_>>` and are not lint-detected, cover their explicit error sections with the focused documentation-contract test.
- Add focused documentation-contract coverage for the guard scope and run Rustdoc/doctests plus the relevant behavior tests.
- Follow Red → Green → Refactor, run `mise run check`, review the implementation iteratively, then verify the completed item through the pinto CLI before committing.

Acceptance Criteria

- [x] Public destructive, multi-record, and persistence APIs include `# Errors` sections describing their relevant validation and I/O failures.
- [x] The API documentation states whether durable partial changes may remain after failure and whether retrying is safe for the documented operations.
- [x] A staged `missing_errors_doc` lint or equivalent guard prevents new omissions in the selected public API scope.
- [x] Rustdoc and focused documentation tests verify that the documented error contracts remain consistent with the exposed result types and behavior.
