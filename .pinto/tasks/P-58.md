# **Summary**

Allow a single sequential `pinto automate` plan to capture IDs produced by earlier commands and reuse them in later commands through zero-based output placeholders, eliminating the need to run a separate add-only plan followed by a second ID-based plan.

# **Implementation Plan**

- Recognize only complete item-ID arguments matching `@command[<zero-based-command-index>].created_ids[<zero-based-output-index>]`; reject malformed, embedded, or non-ID-position tokens with actionable validation errors.
- Keep the existing sequential child-command execution boundary, but add structured JSON producer output for `add` and `split`; consume typed producer results instead of parsing localized human output.
- Validate each command’s normal CLI grammar with safe placeholder IDs before execution, reject future/unknown references before mutation, and resolve valid references immediately before each dependent command.
- Preserve existing literal-ID plans, one-based human/JSON report command indexes, and existing `created_ids`/`updated_ids` fields; report resolved target IDs and ordered split IDs for recovery.
- Run the same resolution flow in an isolated dry-run workspace, document the syntax and consumer positions in the schema/CLI docs, and add integration coverage plus a runnable demo for boundaries, failures, localization, and non-mutation.

# **Acceptance Criteria**

- [x] A plan can reference the actual ID produced by an earlier successful `add` command without predicting numeric IDs or relying on `issued_ids` continuity.
- [x] `split` exposes every created PBI in creation order, and later commands can reference each output individually.
- [x] Placeholder references use zero-based array indexes, such as `@command[0].created_ids[0]`; existing human-facing automation report command indexes remain compatible.
- [x] Placeholder substitution works in every supported item-ID argument position, including `add --parent`/`--depends-on`, `split` source, `show`, `move`, `reorder` IDs and references, `edit` ID and parent, `remove`, `restore`, `dep`, `link`, and `sprint add`/`unassign`.
- [x] Placeholder tokens are replaced only as complete ID arguments and never invoke shell interpolation or command execution.
- [x] Unknown, future, failed, or out-of-range references produce actionable errors and dependent commands are not executed.
- [x] `--dry-run` resolves placeholders against its isolated temporary board, while apply resolves them against the actual board without exposing preview IDs as authoritative.
- [x] JSON automation results report actual producer IDs and resolved target IDs sufficiently for partial-failure recovery without rerunning successful producer commands.
- [x] Producer results are obtained from structured command outcomes rather than localized human-readable output parsing.
- [x] The automation plan JSON Schema and CLI documentation describe producer outputs, placeholder syntax, zero-based indexing, supported consumers, and recovery semantics.
- [x] Tests cover add->edit/reorder, add with parent/dependencies, split with multiple output references, every supported consumer category, zero-based boundary cases, dry-run non-mutation, localized output, and partial failure.
- [x] Existing plans using literal IDs and existing report consumers remain backward-compatible.
