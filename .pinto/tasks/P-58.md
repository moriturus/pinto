# **Summary**

Allow a single sequential `pinto automate` plan to capture IDs produced by earlier commands and reuse them in later commands through zero-based output placeholders, eliminating the need to run a separate add-only plan followed by a second ID-based plan.

# **Acceptance Criteria**

- [ ] A plan can reference the actual ID produced by an earlier successful `add` command without predicting numeric IDs or relying on `issued_ids` continuity.
- [ ] `split` exposes every created PBI in creation order, and later commands can reference each output individually.
- [ ] Placeholder references use zero-based array indexes, such as `@command[0].created_ids[0]`; existing human-facing automation report command indexes remain compatible.
- [ ] Placeholder substitution works in every supported item-ID argument position, including `add --parent`/`--depends-on`, `split` source, `show`, `move`, `reorder` IDs and references, `edit` ID and parent, `remove`, `restore`, `dep`, `link`, and `sprint add`/`unassign`.
- [ ] Placeholder tokens are replaced only as complete ID arguments and never invoke shell interpolation or command execution.
- [ ] Unknown, future, failed, or out-of-range references produce actionable errors and dependent commands are not executed.
- [ ] `--dry-run` resolves placeholders against its isolated temporary board, while apply resolves them against the actual board without exposing preview IDs as authoritative.
- [ ] JSON automation results report actual producer IDs and resolved target IDs sufficiently for partial-failure recovery without rerunning successful producer commands.
- [ ] Producer results are obtained from structured command outcomes rather than localized human-readable output parsing.
- [ ] The automation plan JSON Schema and CLI documentation describe producer outputs, placeholder syntax, zero-based indexing, supported consumers, and recovery semantics.
- [ ] Tests cover add->edit/reorder, add with parent/dependencies, split with multiple output references, every supported consumer category, zero-based boundary cases, dry-run non-mutation, localized output, and partial failure.
- [ ] Existing plans using literal IDs and existing report consumers remain backward-compatible.
