# **Summary**

Make release instructions reusable for every release by removing fixed historical version values and adding a checked pre-tag workflow.

# **Acceptance Criteria**

- [x] Generic release instructions use an explicit version placeholder or a command-derived value instead of a fixed published version.
- [x] The documented pre-tag workflow verifies package versions, committed lockfiles, changelog entries, installation examples, and tag availability.
- [x] Documentation regression tests detect accidental reintroduction of fixed historical release values in the generic procedure.
- [x] The resulting command sequence remains clear and executable for a maintainer preparing a new release.

# **Implementation Approach**

## Scope

The stale value lives in `docs/book/src/reproducibility.md` "Publishing a release", which hardcodes `git tag 0.2.0` / `git push origin main 0.2.0` and cites the `0.2.0` CLI rename. These mislead once the published version moves on (currently `0.4.0`). The concrete published-version examples in `installation.md` / `README.md` are validated by `check-release-metadata.sh` against the latest tag and stay concrete on purpose; they are out of scope.

## AC1 - command-derived version

Introduce `VERSION="$(cargo pkgid | sed 's/.*[@#]//')"` in the generic procedure and reference `$VERSION` in the tag/push commands, so instructions never embed a stale published version. Reword the breaking-change note to drop the `0.2.0` number while keeping the historical CLI-rename illustration.

## AC2 - pre-tag workflow

Add a "Pre-tag verification" subsection. `check-release-metadata.sh` is a POST-tag consistency check (it requires the latest tag to equal the manifest), so it cannot run before the new tag exists. The pre-tag workflow instead verifies, for the bumped-but-untagged tree: package version (`Cargo.toml`), committed lockfiles, the dated `CHANGELOG.md` entry, the installation examples, and tag availability (the `$VERSION` tag does not yet exist). Documented as a copy-pasteable shell block.

## AC3 - documentation regression test

Add a test in `tests/docs.rs` asserting the generic "Publishing a release" procedure contains no fixed `X.Y.Z` literal in its tag/push commands (guards against reintroducing `git tag 0.2.0`) and that the version-agnostic markers are present.

## AC4 - executable clarity

Keep the command block runnable; `cargo pkgid | sed ...` was verified to output the manifest version.

## Demo & DoD

No new demo board is added. This is a pure documentation change, and the existing `demos/single/release-metadata` already anchors the release-metadata gate, so an extra board item would only duplicate `reproducibility.md`. The DoD "corresponding integration test" item is met by the regression test in `tests/docs.rs`. TDD order: failing `docs.rs` test first, then update `reproducibility.md`, then refactor. Close with `mise run check` and dogfooding.
